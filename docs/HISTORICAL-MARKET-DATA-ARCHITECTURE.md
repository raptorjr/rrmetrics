# Historical Market Data Architecture

## Purpose

Provide a durable, provider-independent historical market-data service for Chart Replay, backtesting and future strategy research. RR Metrics stores and indexes data supplied by the user; it does not bundle or redistribute market data.

The first provider is **Historical Futures**, initially accepting OHLCV candle files in CSV and Parquet formats. Tick data is a later capability and must remain a distinct data type.

## Product scope

### First release

- Multiple imported files under one Historical Futures provider.
- CSV and Parquet input.
- OHLCV bars with timestamp, open, high, low, close and optional volume.
- Multiple instruments, timeframes and date ranges.
- Filename and content-based metadata detection, followed by a review step whenever a value is missing or uncertain.
- Import preview and validation before data is accepted.
- Persistent catalogue and data storage.
- File-level detail, re-import detection and deletion.
- A provider-independent query interface for Chart Replay.

### Deliberately later

- Tick/trade data and bid/ask quote data.
- API-connected market-data providers.
- Automated source-priority configuration and conflict-resolution UI.
- Tick replay and tick-sequenced execution simulation.
- Derived timeframe generation and other transformations unless explicitly requested.

## Core design decisions

### 1. A file is an independently owned data source

Every accepted upload receives a stable market_data_file identity. It owns its original uploaded file and its normalized dataset. Every imported record remains attributable to that file.

Do not collapse overlapping records from different files into one shared row during ingestion. This would make safe source deletion and provenance difficult.

Deleting one imported file removes only that file's original and normalized artifacts and its catalogue record. Data from other files remains intact, even when it covers the same instrument, timeframe and timestamps.

### 2. Keep source datasets separate; resolve overlaps at query time

Each source is normalized independently into the canonical OHLCV contract. The market-data query layer combines eligible source datasets for a requested instrument, timeframe and time range.

When two sources provide the same candle timestamp, the query layer must apply an explicit deterministic resolution policy. Until source-priority controls are implemented, ambiguous conflicting candles must not be silently merged or overwritten. The API should expose enough provenance for the caller to identify the selected source and later support user-configurable priority.

Exact duplicate records can be recognized, but their source relationships must still be retained.

### 3. Separate original files, normalized datasets and catalogue metadata

- **Original file:** preserved as uploaded for provenance and possible future reprocessing.
- **Normalized dataset:** canonical RR Metrics representation, stored separately for efficient querying.
- **Catalogue:** SQLite metadata describing provider, file identity, filename, format, fingerprint, detected/confirmed instrument and timeframe, coverage, row count, status, timestamps and storage locations.

All storage paths are generated by the server from internal IDs. Never use an uploaded filename as a filesystem path.

### 4. Common internal OHLCV contract

A bar represents one interval and contains:

- timestamp: UTC epoch time at the start of the bar, with the source timestamp convention recorded during import.
- open, high, low, close: finite numeric prices.
- volume: nullable numeric volume; do not invent volume when absent.
- instrument: canonical instrument identifier plus the source symbol/contract text.
- timeframe: normalized interval identifier.

The import metadata must retain source timezone/timestamp assumptions and any symbol mapping. No timezone should be guessed silently. If the parser cannot determine a required value confidently, ask the user in the review step.

Validation must reject malformed timestamps, non-finite prices, invalid OHLC relationships and duplicate timestamps within one source unless a documented source-specific rule explains them. Missing bars are not synthesized.

### 5. Tick data is a separate future contract

Tick trades and bid/ask quotes are not OHLCV bars. Future tick ingestion must preserve event-level timestamps, event type, price, size and available exchange/sequence metadata. Bid/ask quote events must remain distinguishable from trade events.

Candles may later be derived from tick events, but tick detail must never be discarded or reconstructed from OHLCV data.

## Storage and query technology

SQLite remains the catalogue and application metadata store. Large historical datasets should not be stored as one SQLite row per candle indefinitely.

Use immutable, source-owned normalized Parquet datasets for historical bars. Evaluate DuckDB as the server-side Parquet reader/query engine behind a small market-data service. The service must own the query contract so the rest of RR Metrics does not depend directly on DuckDB or Parquet.

The current container uses Node 22 on Alpine Linux. The DuckDB Node client documents Linux x64 musl support, which is relevant to this deployment. Pin a stable compatible package version and verify clean npm ci, tests and a real Parquet read/write smoke test in the Docker build before relying on it. Do not add an unverified native dependency as part of a schema-only change.

## Catalogue entities

The initial relational model should include:

### market_data_providers

One provider configuration per provider instance and user. First provider type: historical_futures. This makes room for future API-backed providers without changing the market-data contract.

### market_data_files

One row per uploaded file. Includes provider ownership, original filename, input format, byte size, SHA-256 fingerprint, import status, detected and confirmed metadata, date coverage, row count, original and normalized storage keys, and lifecycle timestamps.

A content fingerprint is scoped to the user/provider and used to identify repeated uploads. Re-importing an identical file must not silently create a second copy.

### market_data_file_datasets (or equivalent source-owned dataset metadata)

Describes the normalized dataset owned by a file: data kind (ohlcv initially), instrument, timeframe, row count, time range, schema version and storage key. Keeping this as a separate concept permits one physical upload to contain multiple datasets later, without changing the file's identity.

The initial UI may require one instrument/timeframe per file. If a file contains multiple instruments or timeframes, the preview should identify that and either split it into separate datasets under the same file identity or ask the user to resolve it; never silently discard records.

## Import lifecycle

1. Upload to a temporary server-generated path with size and format checks.
2. Calculate a content fingerprint and check for an existing matching import.
3. Inspect file metadata and a bounded sample of records.
4. Detect format, columns, instrument, timeframe, timestamp unit/timezone, row count and coverage where possible.
5. Validate the entire dataset and collect import statistics.
6. Present a preview. Require user confirmation for uncertain or missing metadata.
7. Normalize into a temporary source-owned Parquet dataset.
8. Atomically move original and normalized artifacts into their final server-generated locations and commit catalogue metadata.
9. Mark the file ready only after both storage and metadata operations succeed. Clean up temporary artifacts on failure.

Imports must be retryable and idempotent. Failed or interrupted imports must not leave partially visible datasets.

## Deletion lifecycle

Before deleting a file, show its metadata and the amount of data it contributes. Deletion removes only the selected file's source-owned artifacts and metadata. Since overlapping datasets are stored separately, deleting one source cannot remove another source's data.

A later provider-level delete must first show the files and datasets affected.

## Provider-independent query interface

Consumers request data by canonical instrument, timeframe and time range. They receive ordered OHLCV bars plus source/provenance information. Consumers must not need to know whether the data originated from CSV, Parquet, a manual upload or a future API provider.

Chart Replay should use this service instead of maintaining its own independent permanent file-import path. Synthetic demo candles remain available as clearly labelled fallback/test data.

## Implementation sequence

1. Add the additive SQLite catalogue schema, market-data storage directories and architecture-level tests.
2. Implement CSV/Parquet inspection, validation and import preview.
3. Implement confirmed import, normalized source-owned storage, listing/detail and safe deletion.
4. Add the Historical Futures provider tile and multi-file management UI in Settings → Providers.
5. Add the common range-query API and connect Chart Replay.
6. Add source-priority controls and more provider adapters.
7. Add tick data as a separate ingestion and query capability.

## Data ownership and repository hygiene

Historical data files supplied by users or licensed from providers must never be committed to the public repository. Tests must use synthetic or explicitly redistributable fixtures.


## User-supplied evaluation sample

The supplied `es-nq-tick-sample-2026-11-09.zip` contains:
- ES and NQ one-minute OHLCV Parquet files (1,380 bars per instrument).
- Separate ESZ6 and NQZ6 trade-tick Parquet files (1,481,669 ES records and 710,815 NQ records).
- Per-minute volume CSVs, a manifest, and SHA-256 checksums.

The supplied Parquet files use Zstandard compression (Parquet codec 6). The one-minute bar schema is `ts, open, high, low, close, volume, trade_count`; the trade schema is `ts, price, volume, bid_sz, ask_sz, trade_count, symbol, exchange`. Timestamp fields are UTC timestamp values, prices are doubles, and count/volume fields are unsigned 32-bit integers.

The first provider release remains OHLCV-only. Do not import tick files as candles or discard their event-level detail; tick ingestion remains a separate later capability. The manifest's file sizes and SHA-256 values were checked against all eight listed archive files. Actual Parquet decoding and bar/tick reconciliation still require a Parquet reader in the project runtime.


## Confirmed import and source deletion API

The inspect endpoint accepts both CSV and Parquet OHLCV files. Confirmation is submitted to `POST /api/market-data/files/:fileId/import`. Files containing multiple source symbols are imported one symbol at a time; the file remains in review until every detected symbol has its own dataset record. A timezone-less timestamp requires an IANA timezone confirmation. Invalid rows are not skipped unless the request explicitly sets `skipInvalidRows: true`.

Normalized datasets are written as source-owned Parquet files with millisecond UTC timestamps. The original upload remains staged until all detected symbols have been imported, then it is moved to the originals directory. Dataset metadata remains linked to the originating file.

File deletion first returns an impact preview (HTTP 409 with `requiresConfirmation`). The caller must repeat the request with `?confirm=true`. The delete operation tombstones the selected original and normalized source files, then deletes only that file's market-data catalogue hierarchy. Other source files with overlapping instrument/timeframe coverage are reported and retained.


### Real Parquet compatibility smoke test

The supplied ES and NQ one-minute Parquet files were run through the actual RR Metrics service functions: inspection, normalization, and bounded range query. Each contained 1,380 valid OHLCV rows, used Zstandard compression and nanosecond timestamps, and was correctly identified as 1-minute UTC data without timezone confirmation. Both normalized to Snappy Parquet and returned all 1,380 bars through the central query service with matching first/last timestamps. The separate ESZ6 and NQZ6 tick files were correctly rejected by the OHLCV inspector because they do not contain OHLCV columns. Their metadata reports 1,481,669 and 710,815 trade events respectively. Tick event decoding/import remains outside the OHLCV first release.


## Current OHLCV reader/writer and query contract

The first OHLCV implementation uses the pure-JavaScript Hyparquet stack:

- `hyparquet` for Parquet metadata inspection and column reads.
- `hyparquet-compressors` for Zstandard and other supported input codecs.
- `hyparquet-writer` for normalized Parquet output.
- Normalized files use millisecond UTC timestamps and Snappy compression. The timestamp column includes a page index for bounded range reads.

DuckDB was not selected for this phase. The pure-JavaScript implementation avoids a native runtime dependency in the Alpine Docker image and has been exercised against the supplied Zstandard-compressed files. Revisit DuckDB only if real workload measurements show that the current reader is insufficient.

Provider-independent endpoints:

- `GET /api/market-data/datasets` lists ready datasets and their source/file provenance.
- `GET /api/market-data/query` returns ordered OHLCV bars for instrument, timeframe and time range, optionally constrained by source symbol or dataset ID.

Source resolution is deliberately conservative. Distinct contract symbols are never automatically merged into a continuous contract. Multiple files for the same instrument/timeframe/source symbol can be combined only when their date coverage does not overlap. If coverage overlaps, the caller must select a specific dataset ID. This prevents silent conflict resolution until explicit source-priority controls are implemented.

Chart Replay now consumes this query API for stored historical data. Its synthetic demo candles and manual CSV upload remain available as separate data sources.


## Phase 2 — trade-tick data contract

Tick ingestion is a separate capability from OHLCV import. The first supported tick input is Parquet trade-print data. It does not represent bid/ask quote updates or resting order-book depth.

The supplied sample's trade schema is:

- `ts`: UTC event timestamp, retaining nanosecond precision.
- `price`: traded price.
- `volume`: contracts represented by the record.
- `trade_count`: number of trades represented by the record.
- `bid_sz` / `ask_sz`: executed volume classifications from source-record fields, not quote sizes or an inferred aggressor-side calculation.
- `symbol`: dated contract identifier.
- `exchange`: source exchange.

Tick events remain event-level records. Equal timestamps are allowed and must not be deduplicated; normalized storage also retains the original row order as a stable tie-breaker. The normalized tick dataset is independently owned by its source file and stored separately from OHLCV datasets. The first tick phase does not change Chart Replay's OHLCV execution model or introduce tick-level order simulation.


## Phase 2 implementation status — trade ticks

The first trade-tick import and storage path is implemented for Parquet trade-print files:

- `market_data_file_tick_datasets` records source-owned tick datasets separately from OHLCV datasets.
- The tick normalizer writes event-level Parquet with `timestamp_ns` as an unannotated INT64, retaining nanosecond precision.
- Original source-row order is retained as a stable tie-breaker. Equal timestamps are valid and are not deduplicated.
- The provider UI can inspect, confirm, import, list, and delete tick datasets alongside OHLCV datasets.
- `GET /api/market-data/tick-datasets` lists ready tick datasets.
- `GET /api/market-data/ticks/query?datasetId=...&startNs=...&endNs=...` reads a bounded range from one explicitly selected source dataset (maximum 250,000 records per request). It does not silently combine overlapping sources.

The supplied `es-nq-tick-sample-2026-11-09.zip` was tested locally against the actual Parquet files. The archive itself and licensed source files are not committed to the repository.

| Dataset | Imported records | Total volume | Trade count |
|---|---:|---:|---:|
| ESZ6 | 1,481,669 | 1,861,062 | 1,481,669 |
| NQZ6 | 710,815 | 766,017 | 710,815 |

Both files had zero invalid rows. The imported totals, first/last timestamps, symbols, and exchange matched the supplied manifest. Normalized Parquet outputs were written and range queries returned the original nanosecond timestamps and source-row ordering, including records separated by one microsecond.

The sample's `bid_sz` and `ask_sz` fields are source-provided executed-volume classifications. They are not best-bid/best-ask quote sizes or order-book depth. RR Metrics preserves them as supplied and does not infer aggressor side.

**Not yet implemented:** tick-driven Chart Replay execution, quote/order-book data, queue position, partial fills, or tick-level slippage/fee simulation. The existing OHLCV Chart Replay remains unchanged.
